Text-to-SQL Agent

给一句中文问题，Agent 自己写 SQL 去查库、跑错了自己改，最后交回答案和那句可审计的 SQL。 这个项目的重点不是把链路跑通，而是建立一套能复现的评测方法，看清它什么时候会悄悄答错、以及结论是否可信。

50道中文评测题
标准答案全部由 SQL 生成
6张自建电商表
专门埋「算账口径」的坑
99条实验汇总
全部 trace / log 留痕
36节实验笔记
每个数字都能查到出处

Python · SQLite · Function Calling　｜　命令行工具，没有网页界面

一道题是怎么走的

模型只能「提出」SQL，真正执行和判分都由代码做；每一步都写进 trace，事后能逐条翻。

1组装提示词

把 6 张表的结构、12 条「算账规矩」和问题一起发给模型。比如「取消和退款的订单不算卖出」「销售额用成交价，不用现价」。

2代码替它跑

代码先检查是不是只读查询，再去 SQLite 执行，最多回 20 行。模型删不了库，也看不到标准答案；报错时把错误递回去让它自己改。

3交卷与判分

回答以 FINAL: 数字 收口，代码拿去和标准答案比（浮点容差 0.01）。只比执行结果，不比 SQL 字符串 —— 同一道题有无数种正确写法。

那道最值得看的错题

真实运行记录，见 demo.py 与 evidence/trace_ra_160523_1_baseline.jsonl

「2026 年 8 月 1 日及之后上架的商品，一共卖出了多少件？」

SELECT SUM(oi.qty) AS sold_items
FROM order_items oi JOIN products p ON oi.product_id = p.id
WHERE p.launched_at >= '2026-08-01';   -- 语法完全正确，数据库一声不吭
24数据库返回 / 模型交卷漏了「有效订单只算已付款、已发货」
19标准答案差的 5 件来自取消 / 退款订单

语法错不可怕，数据库会报错；「跑通了但口径算错」才危险，因为它看上去毫无破绽。这套评测主要就是为抓这类错误而建的。

评测设计：把尺子做对

功能跑通之后，主要工作集中在评测结果的可信度上。

标准答案谁说了算

50 题的答案、典型错值、校验 SQL 全部由数据库生成，不经人工填写；另设 3 条独立路径交叉复核，任一不成立就不生成题库。

判分器会不会误判

离线重放 200 题次判分，查清 9 个「格式不合规」里其实只有 1 个是算对被误判；修正解析层后误判归零。

同一套配置自己会跳多少

先跑 2–3 遍量出自身波动（曾达 8～14 个百分点）。有一回总分三遍都是 58%，底下仍有 21/50 题在对错之间互换。

怎么把时间漂移和真实效果分开

A/B 交替运行，并保留一组「工具返回逐字节相同、完全没被改动」的题作阴性对照；结论看逐题配对差值，不看单次总分。

一次假阳性是怎么被排除的

最后一组实验：总分 +7.0pp。

+8净增的正确题次里，来自没被改动的 48 道对照题这些题的工具返回值逐字节相同，改造根本没碰到它们
−1真正被改动的 2 道题1/4 → 0/4，反而退了

3 次提示都被模型采纳（下一轮 SQL 真加了 COALESCE），但 3 次最终答案仍然全错 —— 模型其实是把年份写成 2022（正确是 2026）才查不到，它没去核对年份，而是把「没查到」抹成 0 交卷。 0 是合法数字、库不报错，比留着 NULL 更难发现：提示被采纳了，错却被藏得更深。 只看总分会得出相反的判断。据此判定该改造无效，未纳入结论。

主要发现

模型能力是主要来源，工程护栏是补充。 换模型 +24～35pp，护栏在弱模型上 +10.7pp、在强模型上 −0.7pp，两组差值都没超过同配置自身波动 → 先量模型天花板，再决定加不加护栏。
工程能修链路，修不了能力。 护栏把「不查库就编答案」变成会去查（工具调用率 69.0%→80.6%），把跑满 6 轮从 8/9/5 次压到 0/0/0；但剩下的错题来自模型写不出复杂 SQL，不是链路断了。
开放式自评对弱模型不可靠。 问「信息够不够」，6/6 全答「够了」；换成字面判断「这条 SQL 里有没有单词 status」，4/4 全对。可行的做法是判定项由代码给死，模型只做可验证的字面判定，是否打回由代码决定。

怎么跑

零成本演示不需要密钥、不联网、不改任何文件；真跑模型才需要 .env，新产物自动写入 evidence/。

python demo.py                    # 三道真题回放：答对 / 悄悄答错 / 假修复
python chat.py "库里有多少个商品？"  # 自己提问，实时看每一轮查库（需要 key）
python 07_test_offline.py         # 23 项离线单测
python 09_test_schema.py          # 提示词一致性 / 防泄题
python 10_analyze.py resultaudit  # 分层 + 机制 + 判分重放

python 03b_batch_eval.py A1       # 现场跑一道题（需要 key，会花一点额度）

chat.py 会逐轮打印模型决定写哪句 SQL、数据库返回什么、何时停止查库；不写 trace、不判分，只用于展示链路。

Python 3.9+openaipython-dotenv 默认模型 glm-4-flash（免费）EVAL_MODEL 可换模型，判卷代码不动

范围与局限

  • 实验在 glm-4-flash 上完成；强模型对照来自早期记录，未参与后续复核。
  • 后期若干提示词 / 上下文改造的准确率收益未超过同配置波动，因此结论以可复现的机制指标为准。
  • 命令行工具，无界面、无并发、无部署；数据库为本地 SQLite 单文件。
