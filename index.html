Text-to-SQL Agent

给一句中文问题，Agent 自己写 SQL 去查库、跑错了自己改，最后交回答案和那句可审计的 SQL。 这个项目真正花时间的不是把它跑通，而是搞清楚它什么时候会悄悄答错，以及我凭什么相信自己的结论。

标准答案全部由 SQL 生成
6张自建电商表
专门埋「算账口径」的坑
99条实验汇总

Python · SQLite · Function Calling　｜　命令行脚本，没有网页界面，不是一个 App

一道题是怎么走的

模型只能「提出」SQL，真正执行和判分都由代码做；每一步都写进 trace，事后能逐条翻。

1组装提示词

把 6 张表的结构、12 条「算账规矩」和问题一起发给模型。比如「取消和退款的订单不算卖出」「销售额用成交价，不用现价」。不写清楚，模型就自己猜。

2代码替它跑

代码先检查是不是只读查询，再去 SQLite 执行，最多回 20 行。所以模型删不了库，也看不到标准答案；报错时把错误递回去让它自己改。

3交卷与判分

回答以 FINAL: 数字 收口，代码拿去和标准答案比（浮点容差 0.01）。只比执行结果，不比 SQL 字符串 —— 同一道题有无数种正确写法。

那道最值得看的错题

真实运行记录，见 demo.py 与 trace_ra_160523_1_baseline.jsonl

「2026 年 8 月 1 日及之后上架的商品，一共卖出了多少件？」

SELECT SUM(oi.qty) AS sold_items
FROM order_items oi JOIN products p ON oi.product_id = p.id
WHERE p.launched_at >= '2026-08-01';   -- 语法完全正确，数据库一声不吭
24数据库返回 / 模型交卷漏了「有效订单只算已付款、已发货」
19标准答案差的 5 件来自取消 / 退款订单

语法错不可怕，数据库会报错；「跑通了但口径算错」才危险，因为它看上去毫无破绽。整个项目就是围绕这类错误建的。

真正花时间的地方：把尺子做对

功能两周前就能跑了，后面全在修「我怎么知道它有没有变好」。

标准答案谁说了算

50 题的答案、典型错值、校验 SQL 全部由数据库生成，不手填；另设 3 条独立路径交叉复核，任一不成立就不生成题库。

会不会把答对的判成错

离线重放 200 题次判分，查清 9 个「格式不合规」里其实只有 1 个是算对被误判；修解析层后误判归零。

同一套配置自己会跳多少

先跑 2–3 遍量出自身波动（曾达 8～14 个百分点）。有一回总分三遍都是 58%，底下仍有 21/50 题在对错之间互换。

会不会把时间漂移当效果

A/B 交替跑，并留一组「工具返回逐字节相同、完全没被改动」的题当阴性对照；看逐题配对差值，不看单次总分。

最干净的一次自我纠错

最后一个实验：总分 +7.0pp，看着像有效。

+8净增的正确题次里，来自没被改动的 48 道对照题这些题的工具返回值逐字节相同，改造根本没碰到它们
−1真正被改动的 2 道题1/4 → 0/4，反而退了

3 次提示都被模型采纳（下一轮 SQL 真加了 COALESCE），但 3 次最终答案仍然全错 —— 模型其实是把年份写成 2022（正确是 2026）才查不到，它没去核对年份，而是把「没查到」抹成 0 交卷。 0 是合法数字、库不报错，比留着 NULL 更难发现：提示被采纳了，错却被藏得更深。 只看总分就会宣布一个彻底无效的改造有效。这个负结论现在是面试里最能讲的一段。

三条结论

模型能力是主食，工程护栏是补丁。 换模型 +24～35pp，护栏在弱模型上 +10.7pp、在强模型上 −0.7pp，两组差值都没跑赢自身波动 → 先量模型天花板，再决定加不加护栏。
工程能修链路，修不了能力。 护栏把「不查库就编答案」变成会去查（工具调用率 69.0%→80.6%），把跑满 6 轮从 8/9/5 次压到 0/0/0；但剩下的错题是模型写不出复杂 SQL，19/19 个收口正文里连 SQL 都没有。
弱模型做不了开放式自评。 问「信息够不够」，6/6 全答「够了」；换成字面判断「这条 SQL 里有没有单词 status」，4/4 全对。所以判定项必须由代码给死，模型只做可验证的字面判定，打不打回由代码决定。

怎么跑

零成本演示不需要密钥、不联网、不改任何文件；真跑模型才需要 .env。

python demo.py                    # 三道真题回放：答对 / 悄悄答错 / 假修复
python 07_test_offline.py         # 23 项离线单测
python 09_test_schema.py          # 提示词一致性 / 防泄题
python 10_analyze.py resultaudit  # 分层 + 机制 + 判分重放

python 03b_batch_eval.py A1       # 现场跑一道题（需要 key，会花一点额度）
Python 3.9+openaipython-dotenv 默认模型 glm-4-flash（免费）EVAL_MODEL 可换模型，判卷代码不动

局限与边界

  • 所有新实验只在 glm-4-flash 上验证；强模型那半张表是早期历史数据、没有重跑，不外推。
  • 后期 4 个提示词 / 上下文改造的准确率收益全在噪声量级，项目价值是评测方法和失败归因，不是刷分。
  • 命令行脚本，没有界面、没有并发、没有部署；数据库是本地 SQLite 单文件。
  • 不是 RAG 项目，也不是多 Agent 协作；核心是语义映射（中文 → 字段）和工程护栏的边界。
