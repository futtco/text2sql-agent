# Text-to-SQL Agent：用中文问数据库，以及一把能信的尺子

> **一句话**：给一句中文问题，Agent 自己写 SQL 去查库、跑错了自己改、最后交回答案和那句可审计的 SQL。
> 这个项目真正花时间的不是把它跑通，而是搞清楚**它什么时候会悄悄答错，以及我凭什么相信自己的结论**。

**在线看**：[一页纸项目介绍](https://futtco.github.io/text2sql-agent/) · [GitHub 仓库](https://github.com/futtco/text2sql-agent) · [简历正文](RESUME.md)

Python / SQLite / Function Calling 的命令行项目，**没有网页界面，不是一个 App**。
代码和实验已完成，所有结论都留在 `NOTES.md` 里，每个数字都能查到出处。

|---|---|---|
| A1 | `SELECT COUNT(*) FROM products` → 20 → 答对 | 链路是通的 |

想看单道题：`python demo.py B5`；列出所有能回放的题号：`python demo.py --list`。

## 这个项目在做什么

一道题走三步，全部留痕：

1. **组装提示词**：把 6 张表的结构、12 条「算账规矩」和问题一起发给模型。规矩例如「有效订单只算已付款/已发货，取消和退款不算」「销售额用下单时的成交价，不用商品现价」。不写清楚，模型就自己猜。
2. **模型写 SQL，代码替它跑**：模型只能提出「我想执行这句 SQL」，代码先检查是不是只读查询，再去 SQLite 执行，最多回 20 行。所以它删不了库，也看不到标准答案。
3. **交卷与判分**：回答必须以 `FINAL: 数字` 收口，代码拿去和标准答案比（浮点容差 0.01）。每一步写了哪句 SQL、返回了什么，都写进 `trace_*.jsonl`，事后能逐条翻。

关键设计：**主指标只比执行结果，不比 SQL 字符串**。同一道题有无数种正确写法，
但「口径算错」的体现一定是数字不对 —— 这才是我真正想抓的东西。

### 那道最值得看的错题

> 问题：2026 年 8 月 1 日及之后上架的商品，一共卖出了多少件？
> 模型 SQL：`... WHERE p.launched_at >= '2026-08-01'`（语法正确）
> 数据库返回：**24** → 模型交卷 `FINAL: 24`
> 标准答案：**19**

差的 5 件来自已取消/退款的订单，按规矩不算「卖出」。
模型漏了 `status IN ('paid','shipped')` 这个口径。SQL 跑得通、库不报错、看上去毫无破绽 —— 整个项目就是围绕这类错误建的。

## 真正花时间的地方：把尺子做对

功能两周前就能跑了，后面全在修「我怎么知道它有没有变好」：

| 问题 | 做法 |
|---|---|
| 标准答案谁说了算？ | 50 题的 `expect`、典型错值 `decoys`、校验 SQL **全部由数据库生成**，不手填；另设 3 条独立路径交叉复核，任一不成立就不生成题库 |
| 模型答对了却判成错？ | 离线重放 200 题次判分，查清 9 个「格式不合规」里其实**只有 1 个**是算对被误判；修解析层后误判归零 |
| 同一套配置自己会跳多少？ | 同配置跑 2–3 遍，先量出自身波动（曾达 8～14pp）；改造差值必须跑赢这个数才算数 |
| 会不会把时间漂移当效果？ | **A/B 交替**跑，并留一组「工具返回逐字节相同、完全没被改动」的题当阴性对照 |
| 会不会挑好看的那遍写结论？ | 看逐题配对差值，不看单次总分；有一回总分三遍都是 58%，底下仍有 21/50 题在对错之间互换 |

**最干净的一次自我纠错**：最后一个实验总分 **+7.0pp**，看着像有效。
拆开后发现净增的 7 个正确题次里，**8 个来自没被改动的 48 道对照题，真正被改的 2 道题反而 −1**。
只看总分就会把一个彻底无效的改造写进简历。这个负结论现在是面试里最能讲的一段（`NOTES.md` 第 36 节）。

---

## 三条结论

1. **模型能力是主食，工程护栏是补丁**：换模型带来 +24～35pp，护栏在弱模型上 +10.7pp、在强模型上 −0.7pp，两组差值都没跑赢自身波动 → 先量模型天花板，再决定加不加护栏。
2. **工程能修链路，修不了能力**：护栏确实把「不查库就编答案」变成会去查（工具调用率 69.0%→80.6%），把「跑满 6 轮」从 8/9/5 次压到 0/0/0；但剩下的错题是模型写不出复杂 SQL，19/19 个收口正文里连 SQL 都没有，工程救不了。
3. **弱模型做不了开放式自评**：问「信息够不够」，6/6 全答「够了」；换成字面判断「这条 SQL 里有没有单词 status」，4/4 全对。所以判定项必须由代码给死，模型只做可验证的字面判定，打不打回由代码决定。

## 怎么跑

环境：Python 3.9+，第三方库只要 `openai` 和 `python-dotenv`，其余都是标准库。
本机解释器的实际路径是 `E:\conda_data\envs\all-in-rag\python.exe`（下文的 `python` 指它）。

### 不花一分钱、0 次 API

```bash
python demo.py                      # 三道真题演示
python 07_test_offline.py           # 23 项离线单测
python 09_test_schema.py            # 提示词 / 防泄题一致性
python 10_analyze.py resultaudit    # 分层 + 机制 + 判分重放（读已有 trace）
```

### 需要密钥的部分

把 `.env.example` 复制成 `.env`，填入自己的 key（变量名必须是 `DEEPSEEK_API_KEY`）。
默认答题模型 `glm-4-flash`（免费）；用 `EVAL_MODEL` 环境变量切换，**判卷代码永远不动**。

```bash
python 03b_batch_eval.py A1                       # 单题调试（样本不足，别拿数字当结论）
EVAL_MODEL=glm-4-flash python 03b_batch_eval.py --ab --repeat 2
# 2+2 遍 × 50 题 = 200 题次，约 40 分钟，会生成新的 trace 和 runs_summary 行
```

完整的复现命令和三个必踩的坑见 `NOTES.md` 第 35 节。
**复现历史实验一定要把开关写全**（`--ab` 默认带着改造 D/E），并去 `runs_summary.jsonl`
核对 `dedup / sqlguard / selfcheck / finalnorm / resultaudit / model` 六个字段，别信命令行记性。

## 能写什么、不能写什么

`RESUME.md` 是可直接粘贴的 5 行正文 + 面试追问应答；`NOTES.md` 第 34 节是完整版，
含每个数字的出处和一份「明确不能写」清单。最要紧的几条：

- 不写「护栏让准确率提升 20 个点」（20 题时代的旧数字，已作废）
- 不写「动态口径路由 / 表关系卡 / 意图门控有效」（差值都没跑赢噪声）
- 不写任何**单次运行**的准确率
- 不写「在强模型上也成立」（强模型那半张表是早期记录，没重跑，不外推）

## 已知局限（别被问穿）

- 所有新实验只在 **`glm-4-flash`** 上验证；强模型对照是早期历史数据，没有补跑，因此不外推。
- 后期 4 个提示词/上下文改造的准确率收益全在噪声量级；项目价值是**评测方法和失败归因**，不是刷分。
- 命令行脚本，没有界面、没有并发、没有部署；数据库是本地 SQLite 单文件。
- 不是 RAG 项目，也不是多 Agent 协作；核心是语义映射（中文 → 字段）和工程护栏的边界。
