# Text-to-SQL Agent

给一句中文问题，Agent 自己写 SQL 去查库、跑错了自己改，最后交回答案和那句可审计的 SQL。
这个项目的重点不是把链路跑通，而是**建立一套能复现的评测方法**，用来分清「模型能力」和「工程护栏」各自贡献了什么。

**在线看**：[一页纸项目介绍](https://futtco.github.io/text2sql-agent/) · [简历用的项目描述](RESUME.md) · [完整实验记录](NOTES.md)

Python / SQLite / Function Calling，命令行工具（没有网页界面）。

---

## 快速开始

```bash
python demo.py          # 不联网、不花一分钱、不改任何文件
```

它回放三道真实跑过的题，每一句 SQL、每个返回值都来自当时的运行记录：

| 题 | 发生了什么 | 说明什么 |
|---|---|---|
| A1 | `SELECT COUNT(*) FROM products` → 20 → 答对 | 链路是通的 |
| **B5** | SQL 语法完全正确、数据库没报错，返回 **24**，正确答案是 **19** | 「跑通了但算错口径」最难发现，语法错反而不可怕 |
| C10 | 模型把年份写成 2022（应为 2026）导致查不到；工具提示 NULL 后，它没核对年份，而是加 `COALESCE` 把 NULL 抹成 **0** 交卷（正确 80836.75） | 提示被采纳了，错误却被藏得更深 |

单看一道题用 `python demo.py B5`；`python demo.py --list` 列出全部 50 个可回放题号。

## 工作方式

1. **组装提示词**：把 6 张表的结构、12 条「算账规矩」和问题一起发给模型。规矩例如「有效订单只算已付款/已发货，取消和退款不算」「销售额用成交价，不用商品现价」。
2. **模型写 SQL，代码替它跑**：模型只能提出「我想执行这句 SQL」，代码先检查是不是只读查询，再去 SQLite 执行，最多回 20 行。模型删不了库，也看不到标准答案；报错时把错误递回去让它自己改。
3. **交卷与判分**：回答以 `FINAL: 数字` 收口，代码拿去和标准答案比（浮点容差 0.01）。每一步写了哪句 SQL、返回了什么，都写进 `evidence/` 下的 trace，事后可逐条翻。

**主指标取执行结果准确率，不比对 SQL 字符串** —— 同一道题有无数种正确写法，但「口径算错」一定体现为数字不对。

### 一道典型的隐蔽错误

> 问题：2026 年 8 月 1 日及之后上架的商品，一共卖出了多少件？
> 模型 SQL：`... WHERE p.launched_at >= '2026-08-01'`（语法正确）
> 数据库返回 **24** → 交卷 `FINAL: 24`，标准答案 **19**

差的 5 件来自已取消/退款的订单，按规矩不算「卖出」；模型漏了 `status IN ('paid','shipped')`。
SQL 跑得通、库不报错、看上去毫无破绽 —— 这套评测主要就是为抓这类错误而建的。

## 评测设计

| 要解决的问题 | 做法 |
|---|---|
| 标准答案谁说了算 | 50 题的答案、典型错值、校验 SQL 全部由数据库生成，不经人工填写；另设 3 条独立路径交叉复核，任一不成立就不生成题库 |
| 判分器会不会误判 | 离线重放 200 题次判分，查清 9 个「格式不合规」里只有 1 个是算对却被误判，修正解析层后误判归零 |
| 同一配置自己会跳多少 | 同配置跑 2–3 遍先量出自身波动；有一回总分三遍都是 58%，底下仍有 21/50 题在对错之间互换 |
| 怎么把时间漂移和真实效果分开 | A/B 交替运行，并保留一组「工具返回逐字节相同、完全没被改动」的题作阴性对照；结论看逐题配对差值，不看单次总分 |

### 一次假阳性是怎么被排除的

最后一组实验总分 **+7.0pp**。把 200 题次按「是否被改动」分层后发现：净增的 7 个正确题次里，**8 个来自工具返回值逐字节相同的 48 道对照题，真正被改动的 2 道题反而减少 1 个正确题次**；而且 3 次提示都被模型采纳（下一轮 SQL 确实加了 `COALESCE`），3 次最终答案仍然全错。据此判定该改造无效，未纳入结论。只看总分会得出相反的判断。

---

## 主要发现

1. **模型能力是主要来源，工程护栏是补充。** 换模型带来 +24～35pp；护栏在弱模型上 +10.7pp、在强模型上 −0.7pp，两组差值都没超过同配置自身波动。合理顺序是先量模型天花板，再决定加不加护栏。
2. **工程能修链路，修不了能力。** 护栏把「不查库就编答案」变成会去查，把跑满 6 轮的题次压到 0；但剩下的错题是模型写不出复杂 SQL，不是链路断了。
3. **开放式自评对弱模型不可靠。** 问「信息够不够」，6/6 次都答「够了」；换成字面判断「这条 SQL 里有没有单词 status」，4/4 次全对。可行的做法是判定项由代码给死，模型只做可验证的字面判定，是否打回由代码决定。

| 机制指标 | 结果 |
|---|---|
| 工具调用率 | 69.0% → 80.6% |
| 跑满 6 轮的题次（三遍） | 8 / 9 / 5 → 0 / 0 / 0；平均轮数 2.50 → 2.13 |
| 判缺后重写的 SQL | 9/9 次真补上 `status` 过滤 |
| 格式不合规里的真误判 | 9 个中 1 个，修正后归零 |

## 运行

环境：Python 3.9+。只有 `demo.py` 不需要安装任何第三方库；其余脚本需要：

```bash
pip install openai python-dotenv
```

注意装依赖和运行时要用同一个 Python（用 conda / venv 时尤其容易弄混）。

```bash
python demo.py                      # 三道真题回放，0 次 API、0 依赖
python 07_test_offline.py           # 23 项离线单测
python 09_test_schema.py            # 提示词一致性 / 防泄题
python 10_analyze.py resultaudit    # 分层 + 机制 + 判分重放，读已有证据
```

要现场跑模型，把 `.env.example` 复制成 `.env` 并填入自己的 key（变量名 `DEEPSEEK_API_KEY`）。默认答题模型 `glm-4-flash`（免费），可用环境变量 `EVAL_MODEL` 切换，判卷代码不随模型变化。

```bash
python 03b_batch_eval.py A1                                  # 单题调试
EVAL_MODEL=glm-4-flash python 03b_batch_eval.py --ab --repeat 2
# 2+2 遍 × 50 题 = 200 题次，约 40 分钟
```

新产生的 trace 与汇总会自动写入 `evidence/`，不会散落在根目录。完整实验记录与开关说明见 `NOTES.md`。

## 数据说明

`shop.db` 是自建的 6 表电商库，订单状态按月分层，专门用来检验「算账口径」是否被正确理解。
`cases.json` 含 50 道中文题（单表 9 / join 13 / 口径 10 / 计算 11 / 越权 7）和 12 条口径规则；标准答案、典型错值、校验 SQL 全部由数据库生成。

## 范围与局限

- 实验在 `glm-4-flash` 上完成；强模型对照来自早期记录，未参与后续复核。
- 后期若干提示词 / 上下文改造的准确率收益未超过同配置波动，因此结论以可复现的机制指标为准。
- 命令行工具，无界面、无并发、无部署；数据库为本地 SQLite 单文件。
